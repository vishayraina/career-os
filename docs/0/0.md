# Career OS — Operator Contract & MVP Specification

## 1. Purpose

Career OS is a thin personal career-operations layer built on top of FreeHire.

Its purpose is to:

- understand the user's career-related intent,
- inspect the user's existing state in FreeHire,
- select and run the appropriate FreeHire capabilities,
- prioritize opportunities according to the user's current mode,
- propose a plan before execution,
- obtain approval where required,
- keep FreeHire state up to date,
- and provide a useful review of work performed during a session.

Career OS is **not** a replacement for FreeHire.

FreeHire remains the system of record for career data and career state.

---

# 2. Core Principle

## FreeHire owns career state.

Career OS should not duplicate information already represented by FreeHire.

This includes, where supported by FreeHire:

- user profile
- skills
- CV/resume
- jobs
- saved opportunities
- applications
- application status
- notes
- email/application correspondence
- other career-related state

Career OS should retrieve this information from FreeHire whenever needed.

### No duplicate persistent state

Career OS should not maintain parallel files or databases such as:

```text
career/profile.md
career/jobs.json
career/applications.json
career/state.json
career/tracks.json
```

unless a concrete requirement emerges that FreeHire cannot represent.

If such a requirement emerges, local state may be introduced deliberately and minimally.

---

# 3. Responsibilities

Career OS owns:

1. Intent interpretation
2. Workflow selection
3. Planning
4. Plan presentation
5. User plan modification
6. Execution orchestration
7. Prioritization
8. Approval gates
9. Replanning when circumstances materially change
10. Session management
11. Session review
12. Ensuring FreeHire state is updated after state-changing actions

FreeHire owns:

1. Persistent career data
2. Job discovery/search
3. Career/profile information
4. Market-fit capabilities
5. CV/resume capabilities
6. Application tracking
7. Notes
8. Mail triage
9. Other career primitives it already provides

Career OS should **reuse FreeHire capabilities rather than reimplement them**.

---

# 4. Operator Philosophy

Career OS should behave like a personal career operator, not like a rigid chatbot or a second career-management application.

The operator should:

- use existing state before doing new work,
- avoid redundant work,
- search only for missing information,
- choose the smallest workflow that satisfies the request,
- preserve user control,
- be proactive in recommendations,
- but never silently perform consequential external actions.

The default principle is:

> **Inspect → Plan → Approve → Execute → Update State → Review**

---

# 5. Existing State First

Before executing a workflow, Career OS should inspect relevant FreeHire state.

It should avoid unnecessarily repeating work.

For example:

If the user says:

> Find me good AI jobs in Germany.

The operator should first determine:

- what relevant jobs are already saved,
- what searches have already been performed,
- what opportunities are already being considered,
- whether existing information is sufficient.

It should then search for what is missing rather than blindly starting from zero.

### General rule

> **Use existing state first. Search or compute only what is necessary to satisfy the current request.**

---

# 6. Modes

Career OS prioritization is contextual.

The same opportunity can have different value depending on what the user is trying to accomplish.

At minimum, the operator should support the concept of a current mode, such as:

### Actual Search

Optimize for opportunities the user genuinely wants to pursue.

Potential considerations:

- career upside
- compensation
- role fit
- seniority
- geography
- visa/relocation feasibility
- probability of success
- company quality
- strategic career value

### Practice

Optimize for opportunities that provide useful interview/application practice or learning value while carrying lower opportunity cost.

### Research

Optimize for information value.

Potential considerations:

- emerging companies
- new AI/ML markets
- interesting technical areas
- skill gaps
- market trends
- future opportunities

The exact scoring model should evolve.

Career OS owns this prioritization layer; FreeHire provides the underlying career/opportunity information.

---

# 7. MVP Workflows

The initial system should contain only a small number of composed workflows.

Do not build a large workflow catalogue prematurely.

## Workflow 1 — Find Opportunities

Purpose:

> Identify and prioritize relevant career opportunities.

Conceptual flow:

```text
Inspect existing FreeHire state
        ↓
Identify what is missing
        ↓
Search FreeHire if necessary
        ↓
Evaluate relevant opportunities
        ↓
Apply Career OS prioritization
        ↓
Present proposed actions/results
        ↓
Save relevant opportunities to FreeHire
```

Stopping point:

> A useful prioritized opportunity set has been produced and persisted.

It does not automatically continue into application preparation or submission.

---

## Workflow 2 — Prepare Opportunity

Purpose:

> Turn an existing opportunity into an application-ready package without submitting it.

Conceptual flow:

```text
Read opportunity from FreeHire
        ↓
Evaluate fit
        ↓
Identify requirements/gaps
        ↓
Tailor CV/materials using FreeHire capabilities
        ↓
Persist resulting state/artifacts
        ↓
Stop
```

Stopping point:

> The opportunity/application is prepared and ready for the user's review.

Submission is a separate consequential action and requires explicit approval immediately before execution.

---

## Workflow 3 — Review Career State

Purpose:

> Understand what changed, what remains open, and what should happen next.

Conceptual flow:

```text
Inspect current FreeHire state
        ↓
Identify recent changes
        ↓
Identify active/open work
        ↓
Identify completed/closed work
        ↓
Prioritize next actions
        ↓
Present review
```

This workflow can be used at the end of a session and can also be invoked independently.

Additional workflows should only be added when a real recurring need appears.

---

# 8. Individual Capabilities

The operator should still allow individual capabilities to be invoked directly where useful.

For example:

```text
Run job search.
Analyze this opportunity.
Tailor my CV for this job.
Review my applications.
Process my recruiter mail.
```

These capabilities should map to existing FreeHire skills wherever possible.

The user should not be forced through a composed workflow when they only need one capability.

---

# 9. Workflow Selection

Career OS should select the smallest appropriate workflow based on the user's request.

It should not invent arbitrary workflow architectures at runtime.

There should be:

- primitive capabilities,
- predefined composed workflows,
- and an operator that chooses between them.

Example:

```text
"Find me jobs in Germany"
        ↓
Find Opportunities
```

Whereas:

```text
"Tailor my CV for this job"
        ↓
FreeHire CV capability
```

The operator may recommend additional work, but recommendations do not automatically trigger additional workflows.

---

# 10. Planning

Before execution, Career OS should present a proposed plan.

Example:

```text
PLAN

1. Inspect your existing saved opportunities.
2. Search for missing AI/ML roles in Germany.
3. Evaluate the strongest matches.
4. Rank them using your current search mode.
5. Save the strongest opportunities to FreeHire.

Nothing will be submitted or sent.
```

The user may modify the plan conversationally.

Example:

> Don't search. Just analyze my existing saved jobs.

The operator should incorporate the change and restate the resulting plan.

---

# 11. Plan Approval

Execution begins only after the user approves the proposed plan.

The user may:

- approve,
- modify,
- remove steps,
- add steps,
- change constraints,
- change the prioritization mode.

After modifications, the operator should present the final resulting plan before execution.

---

# 12. Consequential Actions

Career OS may perform research, analysis, preparation, classification, saving, and other reversible operations autonomously after plan approval.

However, consequential external actions require a final confirmation immediately before execution.

Examples:

- submitting an application
- sending an email
- sending an external message
- making another consequential external change

The confirmation should happen **at the point of action**, not merely at the beginning of a long workflow.

Example:

```text
The application for Company X is ready.

I am about to submit it.

Submit application?
```

Only after explicit confirmation should the action occur.

---

# 13. Replanning

The operator should be able to replan when new information materially changes the approved plan.

Example:

```text
Approved:
Apply to the top 3 opportunities.

During execution:
Job #2 has closed.
Job #3 is no longer accepting applications.
```

Career OS should not silently substitute arbitrary actions.

Instead:

```text
The original plan has changed.

Job #2 is closed.
Job #3 is unavailable.

Proposed revised plan:
1. Apply to Job #1.
2. Replace #2 and #3 with the next two strongest available opportunities.

Approve revised plan?
```

Minor implementation details do not require replanning.

Material changes do.

---

# 14. Prioritization

Career OS owns prioritization.

FreeHire provides opportunity and career information; Career OS decides what is most valuable to pursue given the current context/mode.

Prioritization should consider the user's current objective rather than producing a universal ranking.

The operator should be able to say:

> These are the top opportunities **for your current objective**.

It should also explain the major reasons for a recommendation when useful.

Example:

```text
Recommended: Company A

Why:
- Very strong technical fit
- High career upside
- Strong compensation
- Relevant to your current AI-systems direction
- Reasonable application probability
```

The user retains the final decision.

---

# 15. Multiple Good Actions

When several useful actions are available, Career OS should:

1. identify them,
2. rank them,
3. recommend the highest-value action,
4. let the user choose.

It should not arbitrarily execute whichever action it happens to encounter first.

Example:

```text
You currently have:

1. Application deadline tomorrow
2. Strong new opportunity
3. Recruiter message awaiting response
4. CV needing tailoring

Recommendation:
#1 — handle the application deadline first.

You can choose another action if you prefer.
```

---

# 16. Proactive Suggestions

Career OS may recommend additional useful work discovered during execution.

However:

> **Recommendation ≠ execution.**

Example:

```text
Market-fit analysis found that many relevant roles require
distributed inference experience.

I recommend doing a focused market-gap analysis next.

Run it?
```

The operator should not silently branch into unrelated work.

---

# 17. State Updates

State updates should happen automatically.

Career OS must be meticulous about updating FreeHire after state-changing operations.

The operator should not rely on conversational memory to remember that an action occurred.

Conceptually:

```text
Action
  ↓
FreeHire mutation
  ↓
Verify/update resulting state
  ↓
Continue
```

Examples:

```text
Opportunity discovered
→ save to FreeHire

Application prepared
→ update FreeHire

Application submitted
→ update application state

Mail classified
→ associate/update relevant FreeHire state

Useful research finding
→ persist as a FreeHire note when appropriate
```

FreeHire remains the durable source of truth.

---

# 18. Sessions

A session is a contiguous period of career work.

Session boundaries are intentionally simple:

> **A meaningful time gap starts a new session.**

The system does not need a sophisticated persistent session database.

A session may contain multiple tracks.

Example:

```text
Session
├── Germany job search
├── Company A application
├── Recruiter email
└── CV tailoring
```

The user can switch between tracks during a session.

Career OS should not reject a new track simply because another track is unfinished.

---

# 19. Cross-Session Open Work

Open work is not owned by the session.

It exists in FreeHire.

Therefore, when a new session begins, Career OS should be able to inspect previously active work.

Example:

```text
Session 1:
X, Y, Z started.

Time gap.

Session 2:
User starts W.
```

The operator works on W normally.

When reviewing Session 2, it should also identify:

```text
W → newly opened
X → still open, no new update
Y → completed
Z → status changed
```

This prevents unfinished work from disappearing simply because the user changed tracks.

---

# 20. Session Review

A session review should be concise by default.

It should include:

### Completed

What was actually accomplished during the session.

### Changed

Important changes in FreeHire state.

### Open

Previously active or newly created work that remains unresolved.

### Closed

Tracks/opportunities that were completed, rejected, withdrawn, or otherwise closed.

### Recommended Next Actions

Ranked actions based on the current state and mode.

Example:

```text
SESSION REVIEW

Completed
✓ Searched Germany opportunities
✓ Analyzed 12 jobs
✓ Shortlisted 4
✓ Prepared CV for Company A

Changed
• Company B application moved to interview stage
• Company C opportunity closed

Still Open
• Company A — application ready
• Company D — awaiting recruiter response
• 2 older applications awaiting updates

Recommended Next
1. Submit Company A application
2. Follow up with Company D
3. Review the two older applications
```

No action should be described as completed unless the corresponding FreeHire state reflects it.

---

# 21. Review of Previous Open Work

A session review should not be restricted only to things touched during the current session.

It should surface relevant previously open work when there is a meaningful status change or when the item requires attention.

This allows the review to function as a lightweight reconciliation point between sessions.

---

# 22. No Duplicate Persistent State

The default architecture is:

```text
                    ANTIGRAVITY
                         │
                         ▼
                  CAREER OPERATOR
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       Planning     Prioritization   Sessions
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                      FREEHIRE
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
    Profile            Jobs           Applications
       ▼                 ▼                 ▼
      CV               Notes             Mail
```

Career OS should not create another layer of persistent career state.

If a future requirement proves impossible to represent in FreeHire, local state can be introduced explicitly and only for that requirement.

---

# 23. Future Capabilities

The MVP deliberately does not include:

- LinkedIn automation
- browser-based networking automation
- interview-practice workflows
- complex autonomous scheduling
- a separate career database
- a large workflow catalogue
- automatic external communication without approval

These can be added later without changing the fundamental architecture.

Future integrations should be treated as additional capabilities behind the Career Operator.

For example:

```text
Career Operator
      │
      ├── FreeHire
      ├── Gmail
      └── Browser / LinkedIn (future)
```

---

# 24. Design Rules

The following rules should guide implementation.

### Rule 1 — Don't duplicate FreeHire

If FreeHire can store or retrieve something, use it.

### Rule 2 — Existing state first

Never redo work unnecessarily.

### Rule 3 — Smallest sufficient workflow

Run only what is necessary to satisfy the request.

### Rule 4 — Plan before execution

The user sees and can modify the proposed plan.

### Rule 5 — Consequential actions require final approval

Never silently submit, send, or perform an equivalent external action.

### Rule 6 — State updates are part of execution

An action is not complete until the appropriate FreeHire state has been updated.

### Rule 7 — Replan when reality changes

Material changes require a revised plan.

### Rule 8 — Recommendations are not actions

The operator can suggest additional work without executing it.

### Rule 9 — FreeHire is the durable source of truth

Career OS should remain as stateless as reasonably possible.

### Rule 10 — Build only what is needed

When a real limitation appears, add the smallest capability required to solve it.

---

# 25. MVP Success Criteria

The MVP is successful if the user can sit down in Antigravity and naturally say things such as:

```text
Find me good AI jobs in Germany.

Analyze these three jobs.

Prepare the strongest one for application.

Review my current applications.

What should I work on next?

Session over.
```

And Career OS can:

1. understand the request,
2. inspect FreeHire,
3. avoid redundant work,
4. select the correct capability/workflow,
5. propose a plan,
6. accept modifications,
7. execute the approved plan,
8. update FreeHire state,
9. stop at the correct workflow boundary,
10. request confirmation before consequential actions,
11. replan when necessary,
12. and provide a useful session review.

The MVP should achieve this **without building a second career-management system**.
